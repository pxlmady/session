# Session

Навчальний прототип вебсервісу для запису студентів на консультації з викладачами.

Стек: React + Vite + Material UI (клієнт), Node.js + Express (сервер), PostgreSQL + Prisma ORM (дані).
Запуск лише локальний; PostgreSQL працює в Docker-контейнері, яким керує PyCharm.

## Структура

```
client/              клієнтська частина (React, Vite, MUI)
server/              серверна частина (Express, Prisma)
  prisma/            схема БД (schema.prisma), міграції (migrations/), початкові дані (seed.js)
  scripts/           службові скрипти (перевірка підключення, міграцій та обмежень БД)
  src/               код API: routes → middleware → controllers → services → Prisma
  tests/             інтеграційні тести API (Jest, Supertest)
docker-compose.yml   контейнер PostgreSQL для розробки
.env.example         змінні для контейнера PostgreSQL
server/.env.example  змінні серверної частини (DATABASE_URL тощо)
```

## Вимоги

- Node.js LTS 22.12+ (або 24);
- Docker Desktop (Docker Engine), запущений;
- PyCharm Professional з плагінами Docker і Database Tools.

## Перший запуск

1. Скопіюйте `.env.example` → `.env` і `server/.env.example` → `server/.env`, задайте пароль
   (однаковий у `POSTGRES_PASSWORD` і в `DATABASE_URL`).
2. Установіть залежності (термінал PyCharm, корінь проєкту): `npm run install:all`.
3. Запустіть PostgreSQL: відкрийте `docker-compose.yml` у PyCharm і натисніть ▶ біля `services:`
   (або вікно **Services** → Docker → Docker Compose).
4. Перевірте підключення сервера до БД: `npm --prefix server run db:check`.
5. Застосуйте міграції: `npm --prefix server run prisma:migrate`.
6. Задайте `JWT_SECRET` (щонайменше 32 символи), `ADMIN_EMAIL` і `ADMIN_PASSWORD` у `server/.env`
   (за бажанням `SEED_DEMO_PASSWORD`; див. `server/.env.example`)
   і створіть початкові дані: `npm --prefix server run db:seed`.
7. Запустіть сервер: `npm run dev:server` → http://localhost:3000/api/health
8. Запустіть клієнт: `npm run dev:client` → http://localhost:5173

## База даних

Сутності `User`, `Slot`, `Booking` описано в `server/prisma/schema.prisma` (ТЗ, розділ 9).
Структура БД змінюється лише через міграції Prisma:

- `npm --prefix server run prisma:migrate` — створити й застосувати міграцію після зміни схеми;
- `npm --prefix server run prisma:status` — стан міграцій;
- `npm --prefix server run db:seed` — адміністратор і (якщо задано `SEED_DEMO_PASSWORD`) тестові
  викладачі `teacher1/2@session.local`, студенти `student1/2@session.local` та вільні слоти;
- `npm --prefix server run db:check-migrations` — частковий індекс `Booking_active_slot_unique` є в БД
  і жодна міграція його не видаляє;
- `npm --prefix server run db:check-constraints` — перевірка унікальності email, одного активного
  запису на слот і заборони видалення пов'язаних записів (у транзакції з відкатом, дані не змінюються).

Частковий унікальний індекс `Booking_active_slot_unique` (не більше одного запису `PENDING` або
`CONFIRMED` на слот) додано вручну до SQL міграції `init`, бо Prisma не описує такі індекси в схемі.
Після створення кожної нової міграції (`prisma migrate dev --create-only` для перегляду SQL)
переконайтеся, що вона не містить `DROP INDEX "Booking_active_slot_unique"`, і запустіть
`db:check-migrations`.

## Автентифікація та безпека

| Метод та шлях             | Призначення                               | Доступ          |
| ------------------------- | ----------------------------------------- | --------------- |
| `POST /api/auth/register` | Реєстрація (роль `STUDENT` або `TEACHER`) | Публічний       |
| `POST /api/auth/login`    | Вхід, отримання JWT (`{ token, user }`)   | Публічний       |
| `GET /api/auth/me`        | Дані поточного користувача                | Автентифіковані |

- Захищені запити містять заголовок `Authorization: Bearer <token>`; строк дії токена — 24 години.
- Middleware `auth` перевіряє токен і завантажує користувача з БД, `requireRole(...)` перевіряє роль.
- Паролі зберігаються лише як bcrypt-хеш (вартість 10); відповіді API не містять `passwordHash`.
- Вхідні дані перевіряються схемами Zod (`server/src/validation`), невідомі поля відкидаються.
- Помилки мають єдиний формат `{ "error": { "code", "message", "details": [] } }`.
- helmet (заголовки безпеки), CORS лише для `CLIENT_URL`, не більше 10 спроб реєстрації/входу
  за 15 хвилин з однієї IP-адреси (429).

## Слоти та бронювання

| Метод та шлях                     | Призначення                                                   | Доступ                                      |
| --------------------------------- | ------------------------------------------------------------- | ------------------------------------------- |
| `GET /api/teachers?search=`       | Список викладачів (ПІБ, кафедра), пошук за ПІБ                | Автентифіковані                             |
| `GET /api/teachers/:id/slots`     | Майбутні вільні слоти викладача за часом                      | Автентифіковані                             |
| `GET /api/slots/my`               | Власні слоти з даними про записи                              | Викладач                                    |
| `POST /api/slots`                 | Створення слота (`startAt`, `endAt`, `location`)              | Викладач                                    |
| `PATCH /api/slots/:id`            | Редагування вільного майбутнього слота                        | Викладач (власник)                          |
| `DELETE /api/slots/:id`           | Без записів – видалення (204), із записами – скасування (200) | Викладач (власник)                          |
| `POST /api/bookings`              | Бронювання слота (`slotId`, `topic`)                          | Студент                                     |
| `GET /api/bookings/my?period=`    | Мої записи (`upcoming` – майбутні, `past` – минулі)           | Студент, викладач                           |
| `PATCH /api/bookings/:id/confirm` | Підтвердження запису `PENDING → CONFIRMED`                    | Викладач (власник слота)                    |
| `PATCH /api/bookings/:id/reject`  | Відхилення запису `PENDING → CANCELLED`, слот стає `FREE`     | Викладач (власник слота)                    |
| `PATCH /api/bookings/:id/cancel`  | Скасування активного запису до початку консультації           | Студент (власник), викладач (власник слота) |

- Дата й час передаються у форматі ISO 8601 з часовою зоною (`2026-11-03T10:00:00.000Z` або
  `...+02:00`) і зберігаються в UTC; значення без часової зони відхиляється (400).
- Новий слот і новий час слота – лише в майбутньому, `endAt > startAt` (400). Слоти одного
  викладача, крім скасованих, не перетинаються (409 `SLOT_OVERLAP`); суміжні слоти дозволені.
- Бронювання виконується в транзакції Prisma: умовне оновлення слота `FREE → BOOKED` для
  майбутнього слота, потім створення запису `PENDING`. Із одночасних запитів успішний лише один,
  решта отримують 409 `SLOT_ALREADY_BOOKED`. Частковий індекс `Booking_active_slot_unique`
  додатково не допускає двох активних записів на слот на рівні БД.
- Належність слота та запису перевіряється в сервісах (403 для чужого ресурсу).

## Профіль і керування записами

| Метод та шлях         | Призначення                                           | Доступ          |
| --------------------- | ----------------------------------------------------- | --------------- |
| `GET /api/auth/me`    | Перегляд профілю: ПІБ, email, роль, кафедра або група | Автентифіковані |
| `PATCH /api/users/me` | Зміна ПІБ, кафедри (викладач) або групи (студент)     | Автентифіковані |

- Email і роль через профіль не змінюються (поля відкидаються). Поле іншої ролі (кафедра для
  студента, група для викладача, будь-яке з них для адміністратора) повертає 400; порожній рядок
  очищає кафедру або групу.
- «Мої записи»: студент отримує лише власні записи, викладач – лише записи на власні слоти
  (разом зі скасованими). Кожен запис містить слот (час, місце, статус, викладач) і студента.
  Список упорядковано за `startAt` слота за зростанням. `period=upcoming` – консультація ще не
  завершилася (`endAt` у майбутньому, зокрема та, що триває), `period=past` – завершилася.
- Допустимі переходи статусу запису: `PENDING → CONFIRMED` (підтвердження), `PENDING → CANCELLED`
  (відхилення), `PENDING / CONFIRMED → CANCELLED` (скасування). Будь-який інший перехід повертає
  409 `INVALID_STATUS_TRANSITION`. Після початку консультації підтвердження, відхилення й
  скасування недоступні (409 `BOOKING_STARTED`).
- Відхилення та скасування виконуються в транзакції: слот `BOOKED → FREE` і запис `→ CANCELLED`
  умовними оновленнями; якщо стан змінився паралельно, транзакція відкочується (409).

## Адміністрування та email-сповіщення

| Метод та шлях                     | Призначення                                                      | Доступ        |
| --------------------------------- | ---------------------------------------------------------------- | ------------- |
| `GET /api/admin/stats`            | Користувачі за ролями, слоти, записи за статусами й викладачами  | Адміністратор |
| `GET /api/admin/users`            | Список користувачів (без `passwordHash`)                         | Адміністратор |
| `PATCH /api/admin/users/:id/role` | Зміна ролі (`STUDENT`, `TEACHER`, `ADMIN`), відповідь `{ user }` | Адміністратор |

- Іншим ролям ендпоінти повертають 403, без токена – 401 (TC-13).
- Адміністратор не може змінити власну роль (409 `CANNOT_CHANGE_OWN_ROLE`), тому в системі завжди
  залишається адміністратор. Нова роль діє з наступного запиту користувача (роль читається з БД).
- Записи в розрізі викладачів враховують усі статуси; у статистиці залишаються й користувачі,
  роль яких змінено, якщо вони мають слоти.
- Листи (Nodemailer) надсилаються у фоні після успішної операції: створення запису (викладачу й
  студенту), підтвердження, відхилення, скасування (іншому учаснику), скасування слота з активним
  записом (студенту). Помилка надсилання записується в журнал і не скасовує операцію.
- Нагадування: node-cron за розкладом `REMINDER_CRON` (типово кожні 15 хв) надсилає листи обом
  учасникам підтвердженої консультації, що починається протягом 24 годин, і заповнює
  `Booking.reminderSentAt`, тому нагадування не повторюється.
- Без `SMTP_HOST` листи не надсилаються, а виводяться в консоль сервера (`[email] Кому: ...`).
  Налаштування SMTP – у `server/.env.example`.

## Клієнтський інтерфейс

React Router 7, Material UI 9 з українською локалізацією (`ukUA`), іконки `@mui/icons-material`.
Структура `client/src`: `api/` (виклики REST API), `components/` (спільні компоненти),
`context/` (автентифікація, спливаючі повідомлення), `hooks/` (стан форм і завантаження даних),
`pages/` (сторінки), `utils/` (мітки статусів, дати, перевірка полів).

| Маршрут         | Сторінка                                                  | Доступ            |
| --------------- | --------------------------------------------------------- | ----------------- |
| `/login`        | Вхід                                                      | Гість             |
| `/register`     | Реєстрація (після успіху клієнт сам виконує вхід)         | Гість             |
| `/teachers`     | Список викладачів із пошуком за ПІБ                       | Усі ролі          |
| `/teachers/:id` | Вільні слоти викладача, бронювання з темою (лише студент) | Усі ролі          |
| `/my-bookings`  | Мої записи: «Майбутні» / «Минулі», статуси, дії           | Студент, викладач |
| `/slots`        | Мої слоти: створення, редагування, видалення              | Викладач          |
| `/profile`      | Перегляд і редагування профілю                            | Автентифіковані   |
| `/admin`        | Статистика та керування ролями                            | Адміністратор     |

- Стартова сторінка ролі: студент – `/teachers`, викладач – `/slots`, адміністратор – `/admin`.
  Гість на захищеній сторінці переходить на `/login`, недоступна для ролі сторінка
  переспрямовує на стартову сторінку ролі.
- Токен зберігається в `localStorage`; під час запуску перевіряється запитом `GET /api/auth/me`.
  Відповідь 401 на будь-який запит завершує сеанс і відкриває сторінку входу.
- Статуси показуються текстовими мітками (ТЗ, п. 13.3) і кольором як додатковою ознакою.
  Відхилений запис має статус `CANCELLED` і показується як «Скасовано».
- Дата й час слота вводяться полем `datetime-local` і надсилаються в ISO 8601 (UTC).
- Сторінка `/admin` показує статистику і список користувачів; роль змінюється вибором зі списку з
  підтвердженням, власну роль адміністратор змінити не може.

Для демонстрації з тестовими обліковими записами задайте `SEED_DEMO_PASSWORD` і виконайте
`npm --prefix server run db:seed`. Під час багаторазових спроб входу діє обмеження 10 спроб за 15 хв.

## Тести

`npm --prefix server test` запускає інтеграційні тести на окремій БД з `TEST_DATABASE_URL`
(контейнер PostgreSQL має бути запущений; міграції до тестової БД застосовуються автоматично).
